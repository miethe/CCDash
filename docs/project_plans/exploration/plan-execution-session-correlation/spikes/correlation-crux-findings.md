# Correlation Crux — Level-Granular Session Correlation & Performance Signals

## Summary

The raw *ingredients* for per-level performance signals (loop counts, review counts, tokens/cost timelines) genuinely exist in the ingested session data — at tool-call/log-row granularity, timestamped and orderable. What does **not** exist is (a) a live mechanism that attributes a session or session-segment to a **task**, and (b) any addressable entity at all for **wave** or **acceptance-criteria** level — those levels have no row to attribute *to*, independent of the join. **Phase**-level attribution has a real code path (`session_correlation.py`) but it is gated on the *same* structural failure mode the gap-analysis already proved fatal for feature-level linking: it depends on an explicit slash-command tag with a phase argument, which subagents never carry. So the crux answer is: **feasible only at feature/phase granularity, and only after the base-join fix — task/wave/AC-level correlation requires additional schema/attribution work the base-join fix does not by itself deliver.**

## Correlation Feasibility (level attribution)

`session_correlation.py`'s `correlate_session` is the only extant mechanism that attempts sub-feature attribution, and it is already consumed by the planning session board (`planning_sessions.py:396,576`) and, per its own docstring, intended for reuse by `FeatureEvidenceSummaryService`. It does **not** generalize cleanly to a retro use case for three reasons:

1. **It is a heuristic overlay, not a persisted link.** It runs at query time over whatever's already in `entity_links`, `session_forensics_json`, and `session.task_id` — it does not write anything back, and it is entirely separate from the `_rebuild_entity_links` producer pipeline the gap-analysis audited (`sync_engine.py:5491-6389`). A retro built on `correlate_session` output would be reconstructing correlation on every read, with no persisted provenance and no way for the base-join-fix work (Theme 1) to benefit it directly unless the two pipelines are explicitly merged.
2. **Its phase/task evidence sources are gated by the same structural hole as G-2.** `phase_hint`/`task_hint` evidence requires either an explicit command tag with a phase argument (phase) or the task's frontmatter back-ref pointing at *this* session's ID (task) — both are orchestrator-only surfaces, per the signal table above. Subagents — where gap-analysis G-2 already established the money is spent — get **zero** phase/task evidence from this pipeline; they can only inherit via `_correlate_lineage` (`session_correlation.py:285-311`), which is explicitly "low confidence" and only fires if some ancestor already has a **feature** correlation (it inherits `feature_id`, not phase or task — lineage inheritance is coded for the feature dimension only, not phase/task).
3. **Confidence is qualitative (`high`/`medium`/`low`/`unknown`), not calibrated.** There's no precision/recall measurement anywhere in the codebase for this pipeline (no test asserts an accuracy rate against ground truth); "high" for `phase_hint` and `explicit_link` are trusted by construction, not validated against outcomes.

**Net**: the mechanism generalizes in *shape* (evidence accumulation, confidence ranking) but not in *coverage* — it inherits the orchestrator-only blind spot from the base gap-analysis rather than escaping it, because it is built on the same underlying signals (command tags, frontmatter back-refs) rather than new ones.

## Dependency on Base-Join Fix

The gap-analysis Step 0 / Theme 1 fix (subagent lineage inheritance for feature links + slug normalization + widened evidence surface) is a **necessary but insufficient** precondition. Precisely, what it must deliver before per-level correlation is even attemptable:

1. **Subagent lineage inheritance must exist as a written artifact, not just a query-time heuristic.** Today `_correlate_lineage` inherits `feature_id` only, in a non-persisted service. For level correlation to work, an equivalent inheritance must exist for **phase/task**, and it must be computable somewhere subagents' cost/loop signals can be joined against it (either persisted as `entity_links`/`session_usage_attributions` rows, or the heuristic service must itself be extended and made the retro's data source).
2. **A task-id/phase-id must reach the subagent, not just the orchestrator.** This is the single highest-leverage fix: if `tasks.session_id` inheritance (or an equivalent `subagent_parent_id`→task walk) is added, both the task-level *and* the review-count signal (which lives on the orchestrator's Task-tool-call rows) become joinable to the same task in one pass.
3. **Slug/alias normalization (G-2 fix)** is required before B1 file-path evidence — which is the *only* channel that currently reaches subagent-authored implementation files — can produce any link at all; per the gap-analysis this is still an open, unresolved question (two competing root causes, Step 0 not yet run).
4. **New work the base-join fix does *not* cover, and must be scoped separately:**
   - A `wave` entity does not exist; if wave-level retro signal is required, this is a schema addition, not a join fix.
   - An `acceptance_criteria` entity does not exist; same as above.
   - `session_usage_attributions.entity_type` has no `task`/`phase`/`wave`/`AC` member — extending token/cost attribution to plan levels means writing a new attribution producer analogous to `session_usage_attribution.py`'s existing skill/agent/workflow producers, not extending the base-join.
   - A reviewer-type-agent taxonomy (which subagent names count as "review") does not exist anywhere in code and must be authored (a config list, similar to `session_mappings.py`'s existing mapping-driven approach) before "reviews used" can be counted rather than just enumerated.
   - Loop/retry derivation (file-edit repeats, test fail→pass sequences, tool error→retry pairs) has zero existing derivation logic; the raw rows support it, but a new computation layer is required regardless of join state.

## Deal-Killer Verdict

**Conditional — refuted for feature/phase-level performance signals contingent on the base-join fix; triggered as-scoped for wave/AC-level and for "review counts" as counts (not presence flags).**

- **Refuted for the core ask** ("session correlation to plan levels + performance signals") **if** the ask is narrowed to **phase and task**, and **if** the base-join fix additionally propagates task/phase identity down the subagent tree (not just feature identity, which is all Theme 1 currently commits to). Under that condition, real per-tool-call, timestamped signal exists for file-edit loops, test-run pass/fail sequences, and review-agent invocation counts — it just needs (a) the lineage-inheritance target widened from feature-only to feature+phase+task, and (b) new derivation/aggregation code that does not exist today.
- **Triggered as currently scoped** for two sub-asks explicitly in the charter question:
  - **Wave-level correlation**: impossible — no addressable entity exists in the data model at all. This is not a join gap; it is a missing concept.
  - **AC-level correlation**: impossible for the same reason.
  - **"Review counts" as counts**: the shipped code path (`agentsUsed`) throws the count away by design (`_add_unique`); a *count* signal exists only in raw, undeduped rows that no current query surfaces — this is recoverable, but as scoped ("derive... review counts... from session forensics") it does not exist today and requires new code, not just the join fix.
- **Tokens/cost per level** is the weakest link of all four requested signals: the one piece of infrastructure purpose-built for granular cost attribution (`session_usage_attributions`) explicitly does not model plan-hierarchy entities. This is the strongest evidence that "per-level cost" was never a design target of the current system and will require a new attribution dimension, independent of anything the base-join fix touches.

## Open Questions

- **OQ-1**: Does `related_tool_call_id` on `session_logs` (schema at `sqlite_migrations.py`, producer not traced in this leg) already link a failed tool call to its retry? If yes, error→retry loop counting is materially cheaper than assumed. Needs a dedicated trace of its write path in `claude_code/parser.py`.
- **OQ-2**: Is there a real transcript where an orchestrator invokes a review-type subagent (karen/code-reviewer/senior-code-reviewer/task-completion-validator) more than once, to empirically confirm the undeduped `session_artifacts`/`session_logs` row count actually reflects call count (vs. some dedup happening earlier in the pipeline that this leg didn't trace, e.g. at ingest upsert time)?
- **OQ-3**: Does `session_metadata.relatedPhases` (the live phase-hint producer) actually fire in practice on any measured corpus, or is it — like `launcher`/`profile`/`effort_tier` in gap-analysis G-7 — a configured-but-effectively-dead path? This leg traced the code path but did not query the DB for `session_metadata` populated-rate the way the gap-analysis measured G-7's columns.
- **OQ-4**: Should "wave" and "AC" be modeled as first-class entities at all, or is the intended design that they're derived/virtual groupings over `tasks`/`feature_phases` (e.g., a wave = a set of phases, an AC = a structured field inside a task's `data_json`)? If the latter, "session↔wave/AC correlation" reduces to "session↔task/phase correlation" plus a task-side aggregation step, which changes the deal-killer verdict from "impossible" to "deferred, contingent on task/phase fix." This leg treated wave/AC as needing dedicated rows because none exist, but did not confirm the product intends them to be first-class.
- **OQ-5**: Is `session_usage_attribution.py`'s producer pipeline actually invoked in the current sync path (i.e., are `session_usage_events`/`session_usage_attributions` populated in the live DB), or is this — like several fields in the base gap-analysis — a built-but-dormant subsystem? This leg read the producer code but did not query row counts the way the gap-analysis did for `entity_links`.

## Confidence Rationale

Confidence is capped below 0.8 because: (a) three OQs above (retry linkage, actual dedup behavior, and whether `session_usage_attributions` is live) were identified but not empirically verified against the database the way the source gap-analysis verified its own claims by SQL; (b) this leg did not re-run the gap-analysis's Step 0 experiment, so the phase/task correlation's practical hit-rate (as opposed to its code-path existence) is unmeasured, matching that document's own G-2 caveat ("not settled empirically").
