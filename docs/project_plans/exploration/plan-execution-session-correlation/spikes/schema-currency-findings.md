# Summary

`.claude/skills` is a **symlink** to `/Users/miethe/dev/homelab/development/skillmeat/.claude/skills` — the deployed schemas ARE the upstream (no drift possible between "here" and "there"; there is exactly one copy on disk). The real staleness is **cross-schema drift inside skillmeat itself**: the `artifact-tracking` schema files (`schema_version: 2`, field-reference.md) are a *thinner, older* contract than the `planning` skill's newer `it_schema: 1` "Plan Frontmatter Schema" (`plan-frontmatter-schema.md`), which defines ~45 fields (`wave_plan`, `tier`, `points`, `scores{}`, `validation_commands`, `decisions`, `execution_mode`, `agent_context`, task-level `acceptance_criteria`) that the artifact-tracking YAML schemas never mention and that **CCDash's parsers never extract into structured columns**. Separately, CCDash's `documents.py` parser is remarkably *permissive* — it stores the entire raw frontmatter dict (`frontmatter_json.raw`) and doc-type-scoped subsets (`metadata_json.docTypeFields`) verbatim, so almost nothing is lost at the document level. The real gap is one level down: the **task-list → `tasks` table** pipeline (`backend/parsers/progress.py`) is lossy and has at least one live field-name bug, AC-level `target_surfaces`/`verified_by` live only in **markdown body text** (never frontmatter) so they're invisible to any frontmatter-keyed extraction, and body content itself is **truncated at 5,000 chars** — large plans' AC sections may not even survive into `documents.content`.

**AC structure (`target_surfaces`, `verified_by`) is NOT a frontmatter field in either contract.** It's a **markdown-body convention**: `.claude/skills/planning/references/ac-schema.md` and `.claude/skills/artifact-tracking/scripts/ac-coverage-report.py` define/parse it via regex over the AC section's raw text (`ac-coverage-report.py:36,124-144`), not YAML. This matters directly for ingestion (next section).

# Candidate New/Newly-Ingested Fields

Ranked by expected session↔plan correlation lift relative to implementation cost:

1. **Fix `progress.py`'s `model`→`assigned_model` field-name bug** (1-line fix, `backend/parsers/progress.py:170`). Currently silently reads the wrong key; every progress file authored per the shipped template (`templates/progress-template.md:56` uses `assigned_model`) has this field dropped on the floor. This is the cheapest, highest-confidence fix in the whole audit.
2. **Promote per-task `assigned_model`, `evidence`, `verified_by`, `started`, `completed` into structured `tasks` columns** (or a `tasks.data_json` that preserves the raw per-task dict instead of the lossy `ProjectTask.model_dump()`). Directly strengthens session↔task correlation: `assigned_model` lets a query join "which model was *planned* to run this task" against the session's actual `model_slug`/`model_variant` (already captured per CLAUDE.md's session detection columns) — a plan-vs-actual model-drift signal that doesn't exist today.
3. **Parse AC blocks (`target_surfaces`, `verified_by`, `ac_id`) out of the markdown body**, not just frontmatter. Reuse `ac-coverage-report.py`'s existing regex extraction as a library import into `documents.py` (or a new `backend/parsers/acceptance_criteria.py`) rather than leaving it a standalone gate-time script. This is the single richest untapped signal: `verified_by` already names task IDs, and `target_surfaces` names concrete file paths — both are ready-made correlation keys to sessions that touched those files/tasks.
4. **Lift `documents.content` truncation limit or add a dedicated `content_full`/streamed body storage** for docs with AC sections beyond 5,000 chars — otherwise fix #3 can silently miss ACs in long plans.
5. **Add `wave_plan`, `tier`, `points`/`estimated_points`, `scores{}` to `_DOC_TYPE_FIELD_KEYS["implementation_plan"]`/`["feature_contract"]`** and project `tier`/`points` onto the `features` table as real columns (currently absent). Enables feature-complexity-weighted correlation (e.g., "high-tier features have N sessions/point vs low-tier").
6. **`validation_commands{command,kind}`** — if authored, gives a structured "how was this verified" signal (kind=runtime_smoke/pytest/tsc/etc.) that could cross-reference against session tool-use logs (did a session actually run that command?). Lower authoring adoption today (it_schema is `MAY`-tier for this field) so lower near-term ROI than #1-3.
7. **Reuse the AAR-enrichment extraction pattern generally**: `aar_review_enrichment.py`'s `resolve_linked_task_evidence` already proves feature→document→frontmatter-task traversal is cheap and read-only-safe (Hard Invariant: no LLM import). Lifting it out of the AAR-only module into a general `agent_queries` helper (with persistence, not just per-request computation) would let *other* surfaces (feature detail, session inspector) show the same "planned assignee/model/AC" evidence without re-deriving.

# Open Questions

- **OQ-1**: Is `it_schema: 1` (IntentTree capture) intended to eventually *replace* `schema_version: 2` (artifact-tracking/CCDash) as the canonical frontmatter contract, or are they meant to coexist as parallel, non-overlapping consumers indefinitely? This determines whether CCDash should chase `it_schema` fields directly or wait for a unification pass.
- **OQ-2**: How many *existing* progress/plan files in this repo actually populate `assigned_model` (vs. omitting it, defaulting to sonnet)? If adoption is low, fixing the parser bug (#1) has less immediate correlation value until authoring habits catch up — worth a quick `grep -c "assigned_model:" .claude/progress/**/*.md` before prioritizing.
- **OQ-3**: Does `ac-coverage-report.py`'s regex AC-block parser handle every AC-authoring variant in the wild (nested lists, multi-line `target_surfaces`, ACs without `id:`), or would lifting it into the sync pipeline require hardening first? Only spot-checked its parsing logic, not run against the full corpus of `docs/project_plans/`.
- **OQ-4**: Is there a reason `tasks.data_json` re-serializes `ProjectTask.model_dump()` instead of the raw per-task frontmatter dict — i.e., was the lossy shape a deliberate simplification (e.g., to keep `tasks` table rows bounded/predictable) rather than an oversight? Worth confirming with whoever owns `backend/parsers/progress.py` before assuming it's purely an omission.
- **OQ-5**: `frontmatter.raw` and `metadata.docTypeFields` are stored as JSON blobs on every `documents` row today — what's the actual storage/query cost of this at current corpus scale (hundreds of plan/progress docs)? If it's already non-trivial, promoting more fields to typed columns (candidates #2, #5) competes with just querying the existing blob more aggressively (e.g., SQLite JSON1 functions) instead of a schema migration.
